## Diagnostic fix: generic 503 was a timeout, not bad credentials

User reported "Suggestions are unavailable right now. Please try again shortly." with all AI env vars filled. Diagnosis:

- `.env` had enabled/provider/key/base_url/model/temp/rate_limit/cache_ttl but **no `AI_SUGGESTIONS_TIMEOUT`**, so the old `config/ai.php` default of **3s** applied. No config cache was present.
- With the 3s cap the OpenRouter free model raised `ConnectionException | cURL error 28 ... timed out after 3014 milliseconds`. With a 45s allowance the same key/model returned HTTP 200 in ~2.90s. **The timeout was the entire cause.**
- Fixes applied: default timeout `3` → `20` in `config/ai.php` + `.env.example`; `OpenAiCompatibleClient` now uses `connectTimeout(min(5, $timeout))` so a dead host still fails fast; `AiSuggestionException` gained a log-only `cause` (`missing_key`, `connection_timeout`, `connection_error`, `provider_http_<code>`, `malformed_completion`), and `SuggestionBroker` logs it. The UI message stays deliberately generic.
- Also made `ai.usernames.count` authoritative: `admin.js` no longer sends `count: 6`, and `UsernameSuggestionRequest::suggestionInput()` defaults to `config('ai.usernames.count', 6)`. Added a feature test proving the config value wins when the browser omits count. Current `config/ai.php` counts are 8 titles / 8 usernames (operator-tuned), so the runbook was updated to match.
- `AI-SUGGESTIONS.md` now documents the 20s budget + 5s connect cap, the `cause` label table, and the timeout-first troubleshooting row.
- **Verification:** real `OpenAiCompatibleClient` probe `OK 2.84s`; real `SuggestionBroker` probe with the operator's current `.env` (`AI_SUGGESTIONS_TIMEOUT=30`, model `nemotron-3.5-super-vl:free`) returned 5 real headlines in **3.93s** — a duration that would still fail under the old 3s cap. Focused suites **71 passed (368 assertions)**; Pint 623 files clean; `view:cache` + `npm run build` pass. Cleared compiled views and restored `storage/framework/views/livewire/.gitignore`.
- **Lesson:** whenever this generic 503 appears with valid config, check `AI_SUGGESTIONS_TIMEOUT` and the log `cause` first, then run `php artisan config:clear`. Do not lower the timeout below measured first-token latency.

## Verification: "does the AI_ config in .env work?" — yes, plus a second bug found

Verified every `AI_SUGGESTIONS_*` var maps `.env` → `config/ai.php` → `config('ai.*')` → the outgoing HTTP request (URL, bearer token, model, max_tokens, temperature all matched; key masked). No `bootstrap/cache/config.php`, so env is read fresh. Two vars absent from `.env` fell back to defaults (`max_tokens=300`, `rate_limit=10`); `.env.example` was missing `TEMPERATURE` and `CACHE_TTL` documentation — both added.

**New root cause found:** the operator switched to a *reasoning* model (`nvidia/nemotron-3.5-lightning:free`). It spends `max_tokens` on a separate `reasoning` field; at 300 tokens OpenRouter returns **HTTP 200 with `content: null`, `finish_reason: length`** → the client raised `malformed_completion` → same generic 503. Measured: `max_tokens=300` NULL/`length`, `700` STRING/`stop` (4.79s), `1200` STRING/`stop`. So this was a *different* cause from the timeout one.

Fixes for reasoning models:
- Default `AI_SUGGESTIONS_MAX_TOKENS` `300` → `700` in `config/ai.php` + `.env.example`; added an explicit `AI_SUGGESTIONS_MAX_TOKENS=700` line to local `.env`.
- `OpenAiCompatibleClient`: a well-formed `200` with empty/`null` content is now a **weak completion**, not an outage — logs `AI suggestion returned no usable content` with a fixed cause (`completion_truncated` / `reasoning_only_completion` / `empty_completion`) and returns an empty result so deterministic local fallbacks fill the list. Only a response with no `choices.0.message` still throws `malformed_completion`. No provider text is logged.
- `SuggestionBroker`: empty results are no longer cached (next click can recover after fixing tokens/model).
- Tests: renamed the structural-503 case, added empty-completion degradation + cause-log tests, an uncached-empty broker test, and an endpoint test proving local titles still come back. **75 passed (378 assertions)**; Pint 623 files clean.
- Live verification with the operator's current env (`timeout=30`, `max_tokens=700`): `result=OK elapsed=18.53s count=5`, real headlines. Note some free models take ~18s, so a 20s default timeout is borderline — keep `AI_SUGGESTIONS_TIMEOUT=30` for these.
- Runbook updated: reasoning-model section, `max_tokens` default, weak-completion failure rows, cause tables, config:cache gotcha, troubleshooting rows.

**Two independent causes of the same generic 503 so far:** (1) timeout shorter than first-token latency, (2) reasoning model exhausting `max_tokens` and returning `content: null`. The log `cause` now distinguishes both.
